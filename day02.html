上一章说 Agent = Model + Harness。这一章解决一个非常实际的问题：这套系统该怎么描述、责任该记在谁头上。答案是——用三个互相不能替代的视图看同一个系统，再把能力划进五个责任域。

01为什么要三个视图：一个视图解决一类翻车

书里的原话是：架构设计的难点不在「列出尽可能多的组件」，而在划分责任边界。它举了四个会在规模化之后集中爆发的边界问题：

  • Model 和 Harness 边界不清 → 模型一升级，应用就得重写；
  • 编排逻辑和运行底座（Runtime）不分 → 任务语义和基础设施绑死，换底座等于重做；
  • 上下文（Context）和状态（State）不分 → 把「不完整的对话历史」当成「可恢复的任务事实」；
  • 沙箱、权限、工具描述混在一起 → 把「模型知道某个工具」误解成「模型有权执行这个操作」。

这四个问题在演示阶段都不会暴露，任务一变长、工具一变多、租户一变多就集体冒出来。所以要三个视图分别盯着不同的风险。

图 1 · 同一套系统，三种问法，三类事故

三者不能互相推导：组件齐全 ≠ 责任清晰，责任清晰 ≠ 变更可控。所以讨论某个能力时，先问一句「我们现在说的是哪个视图」。

书里给了一个特别好用的例子——同一个「状态存储」（State Store），在三个视图里是三个不同的东西：

视图这个能力是什么为什么必须这么看
组件视图任务事实的持久化能力不落库，任务就没法断点续跑
平台视图属于「数据与资源面」，通常由共享平台提供决定它是自建还是平台供给，成本和治理强度完全不同
生命周期视图运行阶段产生、调优阶段反复读取的证据来源没有它，就没有可复现的评估，改版也证明不了变好

图 2 · 五个能力责任域，以及「变更必须回流构建」这条硬约束

注意最后一行「调优层」：它不直接修改生产，只产出候选变更（Patch），必须回到构建层形成新版本、过完门禁才允许上线。

责任域它回答的问题（书里的原话）
业务与应用层系统为什么存在、要完成什么、什么结果可以被业务接受。不实现通用智能体能力。
Agent 构建与编排层把模型、编排逻辑、上下文策略、记忆、知识、Skill 和工具组合成「能观察、判断、行动、接受反馈」的任务循环。它只描述和绑定能力，真正的执行由下一层承担。
生产运行层承载跨时间、跨请求的任务：调度、状态持久化、工作区、隔离、恢复、流量治理和资源管理。
治理与控制层谁可以发布、运行和修改 Agent，哪些资源能被访问，版本如何流转，策略如何下发、执行和审计。
调优层从运行中获得轨迹、指标、日志、成本和反馈，通过评估与实验定位问题，形成候选变更与验证证据。

而安全（Security）不属于任何单独一层，它横跨五层：业务层定风险边界，构建层实现约束和验证，运行层提供隔离，治理层定义身份策略审计，调优层用红队和仿真验证这些措施是否真的有效。

03五条设计原则（拿来就能当评审清单）

  1. Model 与 Harness 解耦。模型是可替换的认知核心，Harness 与任务、环境、组织绑定。模型升级可能会让某些补偿性的提示词或循环控制失效，所以两者要一起评估，但实现上不能绑死。
  2. 编排层与 Runtime 解耦。编排层定义「怎么思考和行动」，Runtime 定义「在什么资源和故障条件下持续运行」。分开才能在不重写任务逻辑的前提下换运行底座。
  3. 状态外置，执行实例可替换。会话、计划、待办、工具结果、工作区、记忆、制品都不能只存在模型上下文或某台机器的内存里。
  4. 自主性必须与权限、可验证性匹配。给出的工具、网络、数据、凭证越多，Blast Radius（影响半径，出错时能波及多大范围）越大。要靠最小权限、短期凭证、出站控制、沙箱隔离和审批共同建立边界。
  5. 可观测、安全、评估是运行前提，不是上线补丁。不记录轨迹和环境结果，既无法定位问题，也无法复现评估、证明版本改进。

这五条有个共同点：凡是被授予的自主性，都必须有与之匹配的边界、证据和验证手段；暂时不需要的能力可以不建，但要写清楚什么条件下必须补齐。

04跟我工作有什么关系

① 三个视图就是一份现成的评审清单

下次评审别人的 Agent 方案，按顺序问三句：组件齐不齐（上下文、状态、验证有没有被当成实现细节）？责任清不清（这块是应用团队做还是平台做）？变更可控不可控（改了 Prompt 或模型，怎么证明没变差、怎么回滚）？三个问题里有一个答不上来，方案就不该进开发。

② 前端最容易踩的坑：把 State 放在页面里

原则三「状态外置」对做页面的人最直接：任务状态、待办、已完成的步骤不能只活在浏览器内存或对话历史里，否则刷新一下、换个标签页，任务就"失忆"了。正确做法是后端存任务事实，前端只做「订阅 + 渲染 + 发起中断/接管」。

③ 别把编排逻辑写进业务页面

业务与应用层和构建编排层的边界，落到代码上就是：「这一步该调用什么、什么时候停」属于编排层；「这个业务场景要什么、什么结果算合格」属于业务层。把 Agent 的步骤判断写死在业务页面的 if-else 里，等模型或工具一换就是大面积返工。

④ 一句话模板（写方案时直接用）

「本应用属于业务与应用层，交付 X 结果；编排逻辑放在编排层，通过 Agent Release 版本化发布；任务状态外置在状态存储，运行在受约束的执行环境里；上线前需要过评估门禁。」——这句话里的每一段，对应图 2 里的一行。

06今日自检 3 问

  1. 你负责的系统，如果别人问「这块归谁管」，你能立刻答出来吗？答不出来，说明责任边界还没划。
  2. 任务状态现在存在哪里？如果答案是「浏览器内存 / 对话历史 / 某个进程的内存」，那它还不具备断点续跑的能力。
  3. 最近一次改动（换模型、改提示词、加工具），你能拿出「没变差」的证据吗？拿不出来，就是原则五没落地。
