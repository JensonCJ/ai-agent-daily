第 1 章 · AI 原生应用的新阶段

本页约 8 分钟2 张图 · 3 个判断 · 18 个术语格式 v2

大模型正在从「帮你写东西」变成「替你把事做完」。但这一章最重要的一句是：事情能不能做完，主要不取决于模型有多聪明，而取决于模型之外那套工程系统——书中把它叫 Harness（模型之外的工程系统）。

01这一章在讲什么

上一阶段：应用问，模型答。企业把大模型接进业务，通常靠三件事：写提示词、用 RAG（先查企业内部资料，再让模型照着资料回答）、用 Workflow（工作流：步骤和分支在开发时就写死）。这时候模型负责「理解和生成」，怎么一步步走完，是代码说了算，模型交出来的主要是「内容」。

转折点：模型开始自己走流程。以 Coding Agent（编码智能体：会读代码库、改文件、跑命令和测试的 AI）为代表，模型第一次能长时间自己干活——它自己分步骤、自己调工具、看结果不对再调整，最后交出来的不是一段话，而是能验证的结果（代码改对了、测试过了）。

于是有了全书的第一个公式：Agent（智能体）＝ Model（模型）＋ Harness（模型之外的工程系统）。

图 1 · Agent 是什么：Model 负责「想」，Harness 负责「能干活」

读法：模型是发动机，Harness 是底盘、变速箱、方向盘和刹车。发动机换新能提速，但车能不能上路、会不会失控，取决于后面这几样。所以「我的 Agent 不听话」这个问题，一半以上的答案在右边那一半。

02第一个判断：形态是共存的，不是升级打怪

很多人以为 AI 应用会这样升级：问答 → 工作流 → 副驾 → 智能体 → 多智能体，后一个取代前一个。这一章明确反对这个理解：选哪种形态，看的是「任务的确定性」和「出错的风险」，不是新旧。

形态任务怎么走，谁说了算人做什么什么时候用它
Chat / RAG
问答 / 检索增强		应用预先定好提问、自己判断只要内容，不直接改动外部系统
Workflow
工作流		开发时写死，运行时只有少量分支设计流程、审批路径能穷举、出错代价高
Copilot
副驾		人一步步决定驾驶者，并对结果负责专业判断难自动化，但局部活可以委托
Single-Agent
单智能体		智能体在运行时决定部分或大部分路径定目标、卡审批点、验收路径难预知、环境有反馈、结果可验证、任务有边界
Long-Horizon Agent
长程智能体		按长期反馈持续调整设检查点、处理例外任务要跨会话、要能暂停和恢复
Multi-Agent
多智能体		多个智能体按角色分工、编排定角色、权限、协作边界单个智能体受时间跨度或角色复杂度限制

一句话记法：先用够用的、最便宜、风险最小的那一种（书里叫「最低充分架构」）。低风险的知识助手可以永远停在问答形态。

03第二个判断：L1–L4 是能力级别，不是升级任务

图 2 · 四个能力级别：从「帮你写」到「自己跑并持续变好」

L1–L4 判断的是「这个应用的能力形态」，不是「这家企业的 AI 水平」。同一家公司里，知识助手在 L1、研发智能体在 L3，很正常。

级别长什么样升级要补什么
L1辅助生成问答、检索、基础副驾；人负责把活干完可复用的提示词、知识库、最基础的评测
L2受控自动化工作流，或在工作流里局部用智能体；结果结构化、带审批划清「哪些允许它自己决定」，引入 Harness、工具策略、轨迹评估
L3智能体执行智能体自己持有任务循环：动态规划、操作环境、多步任务、状态持久、失败能恢复运行底座（Runtime）、沙箱（Sandbox）、可观测（Observability）、安全（Security）、评估（Evaluation）
L4规模运营多任务多租户、策略控制、离线＋在线评估、灰度与持续优化共享平台、组织知识、标准与自动化，把治理成本降下来

04跟我工作有什么关系

① 最缺的那一半活儿，恰好是普通工程活儿

模型训练、推理优化确实要专门团队；但 Harness 里的绝大多数事情——上下文怎么组织、任务状态存哪、工具怎么注册、权限怎么判、结果怎么验证——是常规的前后端工程。这就是为什么书里反复说「不要把问题都归给模型」：你缺的可能不是更强的模型，而是右边那半张图。

② 做企业前端的人，会直接撞上三件事

  • 交互范式变了。从「填表单 → 调接口 → 看结果」变成「定目标 → 看进度 → 中途接管 → 验收」。要设计的是人在哪个节点介入（HITL），而不是在旧页面上再挂一个聊天框。
  • 进度展示变了。Agent 的「加载中」不是转圈，而是任务状态机：待办 / 执行中 / 等审批 / 失败可恢复。页面上要能看见它跑到哪一步、断了能不能接着跑，这对前端状态管理是实打实的新要求。
  • 权限审批要有真实落点。书里那句「模型知道某个工具 ≠ 模型有权执行」落到界面上，就是确认页、二次确认、操作留痕、可回滚。用普通输入框伪装审批或上传，就是书里点名批评的「假能力」。

③ 判断一个需求该不该上智能体，问三句话

① 任务的路径能不能提前穷举？能 → 用工作流，别上智能体。不能 → 继续问。② 出错能不能人工兜底或回滚？不能 → 先别上。③ 结果能不能被独立验证（测试、比对、双人复核）？能 → 这里是智能体真正的用武之地（书里叫「反馈信号明确、环境边界清晰、错误代价可控」）。

④ 汇报时别再说「我们要做多智能体」

换成这句：「这个任务的路径不可预知、环境有反馈、结果可验证，所以需要 L3 的智能体执行能力，配套要补运行底座、权限控制和评估。」——同一件事，但这句里每一项都能验收，也直接对应书里的「最低充分架构」。

05今日术语卡

英文中文人话解释
Agent智能体能自己分步骤、调工具、看反馈、把任务做完的 AI 程序。= 模型 + 模型之外的工程系统
Model模型大语言模型本身，只负责理解、推理、生成、做判断；它不会自己记事、不会自己管权限、不会自己验结果
Harness模型之外的工程系统原意是「马具／挽具」。马有劲，但得套上挽具、装上马车才能拉货——Harness 就是给模型套上的那套东西
Agentic Application智能体化应用把智能体放进真实业务里（接数据、接工具、接人），并交付可验证结果的完整应用
Chat / RAG对话 / 检索增强生成RAG 就是：先去企业知识库把相关资料查出来，再让模型照着资料回答，减少瞎编
Workflow工作流把步骤和分支在开发时就写死的流程图，确定性强、好测试、好审计
Copilot副驾AI 出建议，人来操作和负责。任务控制权始终在人手上
Single-Agent单智能体一个智能体、一个有边界的任务，自己跑完。这是最基础的智能体形态
Long-Horizon Agent长程智能体能跑几小时到几天、能暂停能恢复、换台机器也能接着干的智能体
Multi-Agent多智能体多个有不同角色和权限的智能体分工协作。不是「多调几次模型」，而是有角色、有边界的分工
Coding Agent编码智能体会读代码库、改文件、跑命令和测试的 AI，是目前唯一规模化赚钱的智能体场景
Context上下文这一轮要喂给模型的全部信息：任务目标、历史、检索到的资料、工具返回的结果。注意它≠任务状态
State状态任务的事实记录：做到哪一步、待办是什么、哪些已经完成。它必须落到数据库里，不能只活在对话历史里
Memory记忆跨会话留下来的经验，比如「这个客户偏好邮件沟通」。和状态的区别：状态是这次任务，记忆是长期积累
MCP模型上下文协议Model Context Protocol：让模型用统一方式发现和调用外部工具的一套标准接口。相当于「工具的 USB 接口」
Runtime / Sandbox运行时 / 沙箱Runtime 是任务在哪儿跑（进程、调度、恢复）；Sandbox 是把它关起来跑，限制它能碰的文件、网络和数据
HITL人在回路Human-in-the-loop：关键动作必须人点确认才能继续。是一种架构设计，不只是弹个审批框
Trace轨迹把模型调用、工具调用、状态变化一步步记下来的执行流水，是排查和改进的依据

06今日自检 3 问

  1. 你手上的 AI 应用，交付的是「一段内容」还是「一个可验证的结果」？如果是前者，它还在 L1，不用急着往上堆功能。
  2. 出问题时，你的第一反应是「模型不行」，还是先看上下文、状态、工具、权限、验证这五件事有没有做？——先怀疑 Harness，通常更接近真相。
  3. 它现在处于 L1–L4 的哪一级？如果要往上走一级，缺的工程能力具体是哪一项？
