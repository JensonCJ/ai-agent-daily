第 2 章（下）· Agent Release 与生命周期闭环

本页约 9 分钟2 张图 · 5 个阶段 · 14 个术语格式 v2

一句话记住这一章的后半段：Agent 的行为不只由代码决定——模型、提示词、上下文策略、记忆、知识、Skill、工具、预算、运行环境，任何一项变了，行为都可能变。所以发布的单位不能只是「代码版本」，而是一个可复现的 Agent Release。

01为什么「代码版本」不够用

传统应用里，一次发布 = 一份代码。测试过了、灰度过了，就能上线。但 Agent 不一样：书里说得很直白——Prompt 可以在生产里随时改而不留版本，那么任何评估结论都只对当时那一刻成立。

于是白皮书给了一个核心概念：生命周期的最小发布单元不是应用代码，而是一个 Agent Release（可复现的智能体发布单元），它至少要绑定六类要素。

图 1 · 一次 Agent Release 至少要锁住的六类要素

这六类要素可追踪之后，企业才能回答三个问题：生产里某个任务用的到底是哪个版本？失败了能不能复现？这次改动是不是真的变好了（而不只是变了）？

02五阶段闭环：不是瀑布，是循环

白皮书把生命周期主线定为：架构设计 → 构建 → 运行 → 治理 → 调优。注意两个和常识不同的点：「架构设计」是独立的第一阶段（形态、自主性、责任域、权限边界一旦定下来，后面所有成本区间就被锁定了）；调优不直接改生产（改完要回到构建，重新过门禁）。

图 2 · 五阶段闭环，以及唯一的回流通道

图 2-2 里还有两条指向「架构设计」的虚线，意思是：当风险来自形态选择或权限模型本身，而不是某个 Prompt 或某次工具调用时，正确的动作是重新设计架构，而不是继续打补丁。

03本章中段的两组拆分（后面几篇的地基）

由于后面第 3–6 章（构建）和第 7–12 章（运行）会逐项展开，这里只先记住两组最容易含混的拆分。

① 广义 Harness 与 Harness 编排层

广义 Harness = 模型之外的一切（含 Runtime、Sandbox、观测、治理）。但真正「持有任务语义」的只是其中一小块，白皮书把它单独命名为 Harness 编排层：

位于模型与运行环境之间，用于构造上下文、组织任务循环、提供能力、约束行为并验证中间结果的代码、配置与执行逻辑。

它的职责可以概括成一句：决定模型看到什么、能调用什么、什么时候停止，以及结果交付前要过哪些验证。而 Runtime 管的是物理层面的事：任务在哪个实例跑、怎么排队限流、崩了从哪个检查点恢复。两者的接口应该是「任务与状态」，而不是函数调用细节——一旦编排层直接依赖某个 Runtime 的内存结构，解耦就已经被破坏。

② 五类信息对象：不要用一个上下文装下一切

书里专门强调：把 Memory 和 Knowledge 放进同一个向量库，往往会同时失去两类治理能力——一个怕错误经验被反复沿用，一个怕权限越界和信息过期。

04三条容易被忽略的硬规则

  1. 治理不只是「运行之后」的事。权限模型和数据边界在架构设计阶段定，工具策略与审批点在构建阶段实现，Sandbox 与 Runtime 在运行阶段执行，观测与安全分析在治理阶段持续检测，评估与仿真在调优阶段验证变更。自检标准是那句很狠的话：如果某项治理要求只能靠上线后的人工流程补齐，而不能落到策略、接口或数据结构上，它在规模化之后很可能会失效。
  2. 调优不等于让 Agent 在生产里改自己。任何由模型、反馈或轨迹生成的 Prompt、Memory、Skill 或 Harness 补丁，都只是候选变更，必须经过可复现评估、安全检查、版本化、灰度和可回滚发布才能进生产。
  3. 观测、评估、发布是同一条链路。没有可复现的证据，调优只能靠主观印象；没有版本化的发布单元，即使找到改进方向，也证明不了改进来自这次变更。缺任何一环，闭环都会退化成一次性人工调参。

05跟我工作有什么关系

① 你团队改 Prompt 的方式，大概率就是「不合规」的

如果现在是「谁都能在生产后台改提示词，改完直接生效」，那按这一章的标准，你们的任何效果结论都不成立——因为你无法证明这次变好是新 Prompt 带来的。最低成本的第一步：把 Prompt 挪进代码仓库或配置中心，走版本和评审，别留在生产后台里裸奔。

② 前端会直接感受到「版本绑定」这件事

页面上的问题排查会变成这样：用户说「它昨天还好好的，今天答错了」。如果每个任务都能查到它用的是哪个 Release（模型+编排+Prompt+能力清单+运行配置+评估基线），你就能定位是编排改了还是模型换了；查不到，就只能靠猜。这就是为什么「任务详情里显示所用版本」不是一个可有可无的字段。

③ 写需求时，把「上线门禁」写进去

提需求时多写一句：「本次改动的评估数据集与准入阈值是什么？不达标怎么回滚？」——这句话会把「构建 → 门禁 → 运行」这条线显式化，避免上线靠拍脑袋、回滚靠重启。

④ 一张图讲清你们现在的短板

把图 2 的五个阶段画在白板上，逐个问：这一步我们有没有产物、有没有准入机制？多数团队会发现卡在「构建 → 运行」之间没有门禁，或者「运行 → 调优」之间没有可复现的 Trace。这两个缺口，就是下一步该投入的工程能力。

07今日自检 3 问

  1. 生产里现在跑的这套，你能说出它的六类要素分别是什么版本吗？说不出来，就没有复现能力。
  2. Prompt 或 Skill 的改动，走的是「提交 → 评估 → 门禁 → 灰度」还是「后台直接改、即时生效」？
  3. 上一次「效果变好了」，你有证据证明是这次改动带来的吗？没有的话，闭环还没建立。
